# Pipeline scheduling (V1.5)

## Training semantics: never changed

For every global step, on every stage:

```
zero_grad()
run the step's forward/backward actions in schedule order     (M microbatches, loss scaled by 1/M)
optimizer.step()                                              (exactly once)
```

All microbatches of a step use the same parameter version. A schedule only **reorders** forward and backward
work inside a step. Gradients therefore equal single-process gradient accumulation; the test suite checks this
for GPipe and 1F1B, 2–4 stages, M = 2…32, with sync and async transport.

## Schedules

Generated by `runtime/scheduler.py::stage_schedule(schedule, s, S, M, max_inflight)` for any S and M.

**GPipe** (fill/drain): stage s < S−1 runs `F0 … F(M−1)` then `B0 … B(M−1)`. The last stage alternates
`F0 B0 F1 B1 …`, because its loss is local.

**1F1B** (PipeDream-flush style):

```
warmup_s = min(S − s − 1, max_inflight − 1, M)
schedule = F0 … F(w−1)            warmup
           F(w) B0  F(w+1) B1 …   steady state: one forward, one backward
           B(M−w) … B(M−1)         cooldown
```

S=3, M=6:

```
stage 0: F0 F1 F2 B0 F3 B1 F4 B2 F5 B3 B4 B5
stage 1: F0 F1 B0 F2 B1 F3 B2 F4 B3 F5 B4 B5
stage 2: F0 B0 F1 B1 F2 B2 F3 B3 F4 B4 F5 B5
```

**Deadlock freedom:** stage s emits `warmup_s + 1` forwards before it first waits for a gradient, and stage s+1
needs `warmup_{s+1} + 1` forwards before it emits one. Since `warmup_{s+1} ≤ warmup_s` for every S, M and
`max_inflight`, the first gradient always arrives. `tests/unit/test_scheduler.py` simulates both schedules for
S ≤ 6, M ≤ 12 and several caps.

## Memory effect

| | Microbatch graphs held by stage s |
|---|---|
| GPipe | M (for s < S−1), 1 for the last stage |
| 1F1B | min(S − s, M, max_inflight) |

Measured on CPU (3 stages, M=8, see `docs/v1-vs-v1.5.md`): stage 0 holds 8 → 3 microbatches, and its saved
activations drop from 37.9 MB to 14.2 MB. Configure `pipeline.max_inflight_microbatches` to cap it further.

## State machine

Each microbatch of the current step moves through:

```
QUEUED → FORWARD_READY → FORWARD_RUNNING → FORWARD_DONE → SENT_FORWARD
       → BACKWARD_READY → BACKWARD_RUNNING → BACKWARD_DONE → COMPLETE
```

| Event | Effect |
|---|---|
| `ACTIVATION_RECEIVED` | → FORWARD_READY (the last stage also needs its target) |
| `FORWARD_STARTED` / `FORWARD_FINISHED` | the last stage becomes BACKWARD_READY immediately |
| `SEND_COMPLETED` | async sender finished the activation |
| `GRADIENT_RECEIVED` | → BACKWARD_READY (may arrive before SEND_COMPLETED) |
| `BACKWARD_STARTED` / `BACKWARD_FINISHED` | → COMPLETE |

Illegal transitions raise immediately: duplicate activation or gradient, a gradient before forward, an unknown
microbatch. The executor asks the state machine for the next action. Today that is the next entry of the static
schedule, which prioritises backward in steady state and keeps memory bounded. A dynamic policy can replace it
later without touching the executor.

## Routing and queues

* **Inbound:** one reader thread per link puts `(link, packet, tensor)` into a bounded queue (4M+16). When it is
  full, the reader stops reading the socket, which applies TCP back-pressure to the sender.
* **Routing:** packets carry `(step, microbatch)`. Out-of-order arrival across microbatches is normal and is
  buffered per step. Messages for step+1 are held until step+1 starts; anything else is a protocol error.
* **Outbound:** one bounded FIFO per link (default 2M+4 messages), so per-link order is preserved. A full queue
  for longer than `network.timeout_s` is an error, not a hang.

## Stall detection

If a stage makes no progress (no event, no action) for `network.timeout_s`, it raises a `PipelineError` that
includes a state dump:
* the next action and remaining schedule
* each microbatch's state
* buffered activations, targets and gradients
* messages held for the next step
* saved contexts
* pending sends and the inbound queue depth

It also sends ERROR to its neighbours, so the whole pipeline stops rather than hanging.
