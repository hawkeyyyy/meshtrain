# MeshTrain V1.5: baseline audit of V1

This audit was written before any V1.5 change. It records what V1 does, how well it does it, and where
it falls short. Later V1.5 documents compare against it.

## Pipeline schedule (V1)

The schedule is GPipe-style fill/drain, one global step at a time (`runtime/pipeline.py::run_stage`).

* **Stage 0** splits the batch into M microbatches. It runs all M forwards back to back and sends each
  activation (plus the targets) downstream. Only then does it wait for M gradients.
* **Middle stages** are event-driven. They handle packets strictly in arrival order: forward on
  activation, backward on gradient, relay targets.
* **The last stage** runs forward, loss and backward for each microbatch as soon as both its
  activation and its target have arrived. It holds at most one microbatch graph.
* Each stage runs `optimizer.step()` once, after its M-th backward. Training is synchronous and
  equivalent to single-process gradient accumulation (verified; see below).

Consequence: stage *k* (k < S-1) holds the saved graphs of **all M microbatches** at its peak. Its
activation memory scales with the whole batch, not with the pipeline depth.

There is no state machine: the logic is one loop with `if` branches per message type, written for
exactly this schedule.

## Transport (V1)

* `Transport` is a point-to-point, ordered, reliable channel. `TCPTransport` uses length-prefixed
  binary frames with JSON headers; `PipeTransport` is used for same-host processes.
* **Sends are blocking on the compute thread.** Each send runs synchronize → `.to("cpu")` →
  `numpy().tobytes()` → `sendall`, and compute resumes only after the bytes are in the kernel socket
  buffer.
* Receives are already decoupled: one reader thread per link pushes decoded packets into an
  **unbounded** `queue.Queue` inbox.
* Every message allocates fresh memory. A new CPU tensor is made on send; `bytearray` plus
  `torch.frombuffer` are used on receive. There is no pinned memory and no buffer reuse.
* Timeouts exist (`network.timeout_s`), disconnects are detected immediately, and a failing stage
  sends ERROR packets to its neighbours.
* Timing is recorded per lifecycle phase: `detach`, `to_cpu`, `serialize`, `network_send`,
  `deserialize`, `to_device`. There is no overlap accounting, because nothing overlaps.

## Memory accounting (V1)

The planner (`planner/memory.py`) estimates, per stage:

* parameters
* gradients (equal to parameters)
* optimizer state (0x params for SGD, 2x for Adam/AdamW)
* saved activations: in-flight microbatches × (input bytes + autograd-saved bytes measured on the
  `meta` device), × 1.25. In-flight is M for every stage except the last, which holds 1.
* temporary: 2 × the largest layer output

Headroom is `max(15% of total, 0.5 GB)`. Runtime reporting (`Stage.memory_report`) covers params,
grads, optimizer state and peak saved bytes. **Nothing compares estimated against actual memory
before training starts.**

### Known failure, from a real hardware run

Reported in this session from the user's hardware: an RTX 4070 Laptop GPU (8 GB) on Windows plus a
GTX 1050 Ti Mobile (4 GB) on Debian 13, over a home LAN.

* The capacity experiment's 2-stage plan for a 475M-parameter model passed the planner, then hit a
  real CUDA OOM on the 1050 Ti ("Tried to allocate 26.00 MiB").
* Missing from the estimate, and the likely causes:
  * AdamW step temporaries (the foreach implementation allocates parameter-sized intermediates)
  * the CUDA context, which counts against `total_memory` but is not in the budget
  * allocator fragmentation
  * transport staging copies
* The same experiment's single-GPU row for the RTX 4070 (475M OK at 0.117 steps/s) was most likely
  inflated by the Windows driver's **CUDA Sysmem Fallback**, which pages to system RAM. V1 cannot
  detect that.

## CPU baseline benchmark (audit environment)

Setup:

* Model: tiny Transformer, 6 blocks, d=256, vocab 512, seq 64 (5.4M params)
* 3 stages, layers `[0,3) [3,5) [5,8)`, each in its own process
* Loopback TCP, AdamW, batch 32, 12 steps (first 2 excluded from the averages)

| M | stage | step ms | fwd ms | bwd ms | comm ms | idle ms | peak saved act MB | MB sent/step |
|---|---|---|---|---|---|---|---|---|
| 4 | 0 | 441 | 92 | 179 | 3.1 | 153 | 73.6 | 2.1 |
| 4 | 1 | 435 | 99 | 181 | 6.2 | 133 | 75.6 | 4.2 |
| 4 | 2 | 430 | 95 | 181 | 2.6 | 139 | 20.5 | 2.1 |
| 8 | 0 | 412 | 105 | 182 | 4.6 | 107 | 73.6 | 2.1 |
| 8 | 1 | 413 | 123 | 180 | 7.0 | 86 | 66.2 | 4.2 |
| 8 | 2 | 422 | 106 | 189 | 3.4 | 111 | 10.2 | 2.1 |

Loss trajectories are identical for M=4 and M=8 (6.3931 → 6.2774 → 6.1617 … 5.3287), as gradient
accumulation requires.

Observations:

1. **Upstream activation memory does not shrink with more microbatches.** Stage 0 holds 73.6 MB at
   both M=4 and M=8, because it keeps every microbatch of the batch. 1F1B should bound this to about
   (S − stage) microbatches.
2. **Idle time is 20–35% of each step.** That is the fill/drain bubble.
3. **Loopback communication is cheap** (3–7 ms/step), so this host cannot show transfer overlap. V1.5
   benchmarks add a clearly-labelled *emulated link* (bandwidth/latency throttle on the sender) for
   overlap experiments.

## V1 limitations that V1.5 addresses

| Limitation | V1.5 milestone |
|---|---|
| Blocking sends on the compute thread | M3 async transport |
| Unbounded receive inbox | M3 bounded queues |
| Fresh allocation per message, no pinned staging | M4 buffer pools / pinned memory |
| Fill/drain schedule; upstream holds all M microbatches | M2 state machine, M5 1F1B |
| No overlap measurement | M7 overlap accounting, M11 timeline |
| Memory estimate misses optimizer temporaries / context; no runtime check | M8 |
| MPS adapter present but untested in pipelines | M9 |
| Planner ignores D2H/H2D cost and overlap | M10 |

Out of scope (V2): moving weights or optimizer state between workers, RAM/NVMe offload, remote
tensor storage, and mid-training repartitioning.
