# MeshTrain V1.5 Architecture

V1.5 turns V1's static distributed pipeline into a reasonably efficient heterogeneous training runtime.
**Placement is still static**: a stage is materialised on one worker at startup and stays there until the
job ends. See `docs/architecture.md` for the V1 foundations (coordinator, worker, distributed-autograd
boundary, protocol). This document covers what changed.

## Version definitions

| | Placement | Transport | Schedule | Devices | Memory |
|---|---|---|---|---|---|
| **V1** | static | blocking sends | GPipe-like | CUDA pipeline | estimate only |
| **V1.5** | static | async per-link senders, pinned staging, buffer reuse | 1F1B (GPipe kept) | CUDA + MPS + CPU | full accounting, runtime validation, startup replan, TensorStore interfaces |
| **V2** (not implemented) | training state placed independently of compute | + prefetch | + dynamic | | RAM/NVMe offload, eviction, memory tiers, virtual distributed tensor memory |

## What changed

```
             compute thread (per stage)                      transport threads (per link)
   ┌──────────────────────────────────────────────┐   ┌───────────────────────────────────────┐
   │ StageStateMachine (schedule: 1f1b | gpipe)   │   │ recv-<link>: TCP → buffer from pool    │
   │  next action ─► ready? ─► FORWARD / BACKWARD │◄──┤   (in place) → event queue (bounded)   │
   │      ▲ events: ACTIVATION_RECEIVED,          │   │                                        │
   │        GRADIENT_RECEIVED, SEND_COMPLETED ... │   │ send-<link>: bounded FIFO → finish D2H │
   │  begin_h2d early · finish_h2d before use     │──►│   (event-ordered) → zero-copy TCP send │
   │  optimizer.step() once per global step       │   │                                        │
   └──────────────────────────────────────────────┘   └───────────────────────────────────────┘
                  │ every phase is an interval span → runs/<id>/timeline.json
```

| Area | Module | Notes |
|---|---|---|
| Schedules + state machine | `runtime/scheduler.py` | `stage_schedule(schedule, s, S, M, max_inflight)`; explicit microbatch states and events ([pipeline-scheduling.md](pipeline-scheduling.md)) |
| Executor | `runtime/pipeline.py` | follows the schedule, routes out-of-order arrivals by `(step, microbatch)`, stall detector with state dump |
| Async sends | `runtime/outbox.py` | bounded per-link FIFO, back-pressure, errors re-raised on the compute thread |
| Buffers | `runtime/buffers.py` | `BufferPool` (pinned or pageable), deferred release on device events |
| Device staging | `worker/device.py` | `begin_d2h` / `begin_h2d` / `finish_h2d` / `after_use`; CUDA uses a transfer stream ([performance.md](performance.md)) |
| Capabilities | `worker/capabilities.py` | `supports(op, dtype)` from real probes; the planner excludes incapable workers |
| Memory | `planner/memory.py`, `runtime/memory_check.py` | [memory-accounting.md](memory-accounting.md) |
| Planner | `planner/partition.py`, `planner/cost.py` | D2H + network + H2D per boundary (both directions), overlap-aware stage time, boundary-size tie-break, `topology_aware` strategy |
| Timeline | `runtime/timeline.py`, `runtime/trace_report.py` | overlap / exposed / idle derived from intervals; Chrome trace |
| V2 interfaces | `runtime/tensor_store.py` | `MemoryTier`, `TensorRole`, `TensorStore`, `LocalTensorStore`, stable tensor IDs |
| Link emulation | `networking/emulation.py` | experiments only; always labelled |

## What remains static (by design)

```
placement decided at startup → stage weights materialised → stage stays on the same worker → job completes
```

V1.5 has no migration, tensor paging, remote optimizer-state storage, or layer movement during training. The
one exception is **startup replanning**: if a stage does not fit, it fails during startup (before any tensor is
exchanged), its device memory is released, and the coordinator plans again with that worker's measured budget.
That replans an attempt; it does not migrate a running job.

## Where overlap happens

| Overlaps with compute | How |
|---|---|
| Socket sends | sender thread per link (async transport) |
| Socket receives and deserialisation | reader thread per link (already in V1) |
| CUDA device→host copies | transfer stream, ordered after compute with an event, waited for on the sender thread |
| CUDA host→device copies | started on the transfer stream as soon as data arrives; the compute stream `wait_event`s just before use |
| MPS copies | **not overlapped**: done synchronously on the compute thread (see [mps.md](mps.md)); MPS stages still overlap send/receive |

Overlap is measured, not assumed: `overlapped = |compute ∩ communication|`, computed from timeline intervals of
all threads. Blocking sends can never overlap compute; the tests check that.

## Why MPS does not need NCCL

Stages never run collectives. Each boundary is an explicit point-to-point message: tensor → host bytes → TCP →
host bytes → tensor. Any backend that can copy to and from host memory can join. CUDA and MPS stages never
share a communicator, a process or a driver.

## Why this is still not virtual VRAM

Every kernel reads only the local device's memory, and every tensor stays on the worker that owns it. MeshTrain
aggregates the memory of several devices by **partitioning the model**. It does not page tensors between
devices or tiers. V1.5 only adds the vocabulary for that (tensor IDs, roles, tiers, `TensorStore`).
`LocalTensorStore.evict` raises `NotImplementedError` on purpose.

## Interfaces prepared for V2

* `TensorStore.locate / put / get / evict / prefetch`, with `MemoryTier` covering local/remote
  accelerator, RAM, NVMe and recompute.
* Stable tensor identities: `model.layers.17.qkv.weight`, `...grad`, `...optim.exp_avg`,
  `act.s3.mb2.stage1.input`. These IDs are already identical whichever worker owns a layer.
* `TensorMeta` (id, owner, shape, dtype, bytes, role, tier). Byte totals per role appear in every step's
  metrics (`memory.tensor_store`).
* `PlacementPolicy`, `RecomputePolicy`, `CompressionPolicy`, `MigrationPolicy` remain placeholders in
  `meshtrain/future.py`.
* The scheduler state machine makes readiness explicit, so a dynamic policy could replace "next action in the
  static schedule".
