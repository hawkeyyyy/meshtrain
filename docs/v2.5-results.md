# MeshTrain V2.5 results: remote RAM as a backing tier

**Question:** can another computer's RAM let the same GPU train a model that does not fit in its own
VRAM plus a constrained local RAM budget?

**Answer, measured on two real machines:** yes. Under identical budgets the largest trainable model went
from 42.1M parameters (static) to 81.4M (local RAM offload) to **160.1M with fedora's RAM**. Every
remote run's losses are bit-identical to a reference run without remote memory. The price is speed:
at 160.1M a step took **179 s**, because about 3.8 GB crossed a 154 Mbit/s Wi-Fi link every step.

> MeshTrain exposes remote RAM as a managed backing tier for distributed tensor state. It does not
> combine the machines' RAM into one physical memory space. GPU kernels read only local VRAM, and remote
> tensors are explicitly staged before computation.

Architecture and protocol: [v2.5-remote-memory.md](v2.5-remote-memory.md). Baseline:
[v2.5-baseline.md](v2.5-baseline.md). Raw data (JSON + CSV per trial): [data/v2.5/](data/v2.5/).

## Environment

| | |
|---|---|
| Compute | `hawkey`: Windows 11 laptop, RTX 4070 Laptop GPU 8 GiB, 15.4 GiB RAM (**about 3.7 GiB free** during the runs), torch 2.6.0+cu124 |
| Remote RAM | `fedora`: Fedora x86_64, CPU only, 15.3 GiB RAM, lends up to 4 GiB and keeps 2 GiB for its OS. It had about 7.5 GiB available at the start (other applications, mostly Gradle/Kotlin daemons, held the rest). |
| Link | home LAN, laptop on Wi-Fi. `meshtrain remote status --probe`: **RTT 3.9–6.4 ms, 154–162 Mbit/s** sustained (32–64 MB echo) |
| Code | branch `feature/remote-tensor-memory` (commits `2649258`…`1aabb74`) |
| Not measured | MPS compute with remote RAM; more than one RAM worker |

**Budgets.** The spec suggests 2 GiB GPU / 4 GiB local / 8 GiB remote. That is not possible on these
machines today: hawkey had about 3.7 GiB of RAM free and fedora about 7.5 GiB. Every experiment therefore
used the same scaled, explicit budgets:

| | Budget | Enforcement |
|---|---|---|
| GPU | **1 GiB** | hard CUDA allocator cap (real OOM beyond it) + TensorStore ledger |
| Local RAM (hawkey) | **1.5 GiB** of MeshTrain model state | TensorStore ledger: startup reservations + staging |
| Remote RAM (fedora) | **3.5 GiB** | reserved on fedora before training; fedora refuses more |

Model family: tiny_transformer, hidden 1280, 8 heads, seq 64, vocab 1024 (one block = 19.7M parameters).
AdamW lr 3e-4, batch 8 in 4 microbatches. Static/local trials ran 3 steps, remote trials 2. The first
step of each trial is excluded from timings. Offload strategies use the CPU optimizer, layer-major
reuse and prefetch distance 1, and build the model one layer at a time. Each trial runs in a fresh
process.

## Primary result: capacity (`data/v2.5/remote-capacity-20261006-143303`)

| Strategy | GPU budget | Local RAM | Remote RAM | Max params | Step time at max | First failure |
|---|---|---|---|---|---|---|
| Static (V1.5) | 1 GiB | – | – | **42.1M** | 0.05 s | 61.7M: CUDA out of memory (1 GiB cap) |
| Local offload | 1 GiB | 1.5 GiB | – | **81.4M** | 0.22 s | 101.1M: needs 1.58 GB local RAM > 1.42 GB usable |
| Remote offload | 1 GiB | 1.5 GiB | 3.5 GiB | **160.1M** | **178.9 s** | 199.5M: grads + staging need > 1.42 GB local RAM |

    P_remote_max (160.1M) > P_local_max (81.4M) > P_static_max (42.1M)

    capacity_gain_vs_static = 160.1 / 42.1 = 3.81x
    capacity_gain_vs_local  = 160.1 / 81.4 = 1.97x

Remote-offload trials in detail:

| Params | Remote layers | fedora RAM used | hawkey local RAM peak | GPU peak reserved | Network per step (read + written) | Step |
|---|---|---|---|---|---|---|
| 81.4M | 0 (fits locally) | 0 | 1.21 GB | 0.79 GB | 0 | 0.23 s |
| 101.1M | 6 of 7 | 0.91 GB | 1.44 GB | 0.91 GB | 0.91 + 0.91 GB | 76.4 s |
| 120.8M | 7 of 8 | 1.13 GB | 1.60 GB | 0.96 GB | 1.13 + 1.13 GB | 132.0 s |
| 160.1M | 10 of 10 | 1.79 GB | 1.60 GB | 1.05 GB | 2.01 + 1.79 GB | 178.9 s |

All budgets held: local RAM peak 1.49 GiB ≤ 1.5 GiB, GPU ≤ 1 GiB reserved, fedora ≤ 3.5 GiB. The 199.5M
failure is the *local* limit. Every remote layer still keeps its gradient accumulator (4 B/parameter)
plus staging on hawkey, and at 199.5M those no longer fit 1.5 GiB. Remote RAM itself was not exhausted.

## Correctness on the real link

The same model with the same budget ran without remote memory and without a local RAM budget, so it
needed more local RAM than the 1.5 GiB limit. The losses are identical to the last bit:

| Params | Reference (no network) | Remote offload via fedora |
|---|---|---|
| 101.1M | 7.116205453872681, 7.125766038894653 | 7.116205453872681, 7.125766038894653 |
| 120.8M | 7.067322492599487, 7.162599086761475 | 7.067322492599487, 7.162599086761475 |
| 160.1M | 7.058249354362488, 7.158302903175354 | 7.058249354362488, 7.158302903175354 |

Loopback tests (`tests/integration/test_remote_offload.py`) compare every step's loss, gradients,
parameters, logits and AdamW state. Remote offload is bit-exact against static training on CPU, and on
CUDA bit-exact against local offload with the same CPU AdamW. The stress test runs 100 steps with no
divergence, no leaked remote or local memory, no queue growth and no stale versions. Every remote
write went through the version check (`old_version → new_version`), and no conflicts occurred.

## Where the time goes (160.1M)

| | Per step |
|---|---|
| Step | 178.9 s |
| Forward + backward, including blocking remote fetches | 30.1 s |
| Optimizer step: stage params + AdamW state, CPU AdamW, write back, commit | 148.1 s |
| Remote fetches | 15 (1.5 per remote layer), 2.01 GB |
| Remote writebacks | 10 (one per layer: params + 2 AdamW tensors), 1.79 GB |
| Remote fetch time exposed / hidden by prefetch | 117 s / 194 s (summed over 2 concurrent connections) |
| Waiting for writeback commits | 60.5 s |
| H2D / D2H | 1.03 GB in 0.31 s / 1.82 GB |
| `remote_reuse_ratio` | 0.70 |

The optimizer step dominates. Each remote layer's master weights **and** both AdamW moments go there
and back every step (about 3 × 4 B/parameter each way). Compute is a rounding error next to Wi-Fi
transfers: the link ran at about 21 MB/s combined, the measured link limit.

| Remote at 81.4M (nothing remote) vs local at 81.4M | 0.23 s vs 0.22 s | 1.05× (no network cost when nothing is remote) |

## Reuse on vs off (`data/v2.5/remote-reuse-prefetch-20261006-143956`, 101.1M, real link)

| Reuse | Step | Remote read per step | Fetches per remote layer per step | remote_reuse_ratio |
|---|---|---|---|---|
| off (per-microbatch residency) | 106.4 s | 1.50 GB | 2.33 | 0.0 |
| **on** (layer-major) | **76.4 s** | **0.91 GB** | **1.17** | **0.50** |

Losses are identical. Reuse cut network reads by 39% and step time by 28%. The gain is smaller than on
loopback (5× fewer fetches, see below), because at this budget 5 of 7 layers stay resident on the GPU.
Those are fetched only for the optimizer step, which reuse cannot avoid. On loopback, with every layer
offloaded, reuse cut fetches from 10 to 2 per layer per step (`tests/integration`, 4 microbatches).

## Prefetch distance (101.1M, real link)

| Distance | Result |
|---|---|
| 0 | 67.1 s/step, 0.66 + 0.66 GB per step, exposed fetch 44.1 s |
| 1 | 76.4 s/step (capacity run above), 0.91 + 0.91 GB, exposed fetch 53.5 s |
| 2 | *not measured*: fedora refused the reservation (its free RAM had dropped to 0.96 GB) |
| 3 | does not fit: look-ahead staging needs 1.55 GB of local RAM > 1.5 GiB budget |

Distance 0 was *faster*, but not because prefetching hurts. A shorter look-ahead reserves less local
staging, so the planner kept more layers locally homed and sent less over the network (0.66 vs 0.91 GB).
Under a hard local RAM budget, prefetch distance competes with capacity for the same RAM. Both are
reported as measured. The distance 1 and 2 points at equal placement remain open.

## Bandwidth sensitivity (loopback, emulated link, `data/v2.5/remote-bandwidth-sweep-loopback-20261006-140057`)

81.4M, GPU 2 GiB cap, local RAM 1.2 GiB, so 4 layers are remote. Each direction of the client connection
is throttled with `EmulatedLink`. This is emulated, not a real network:

| Link | Step | Exposed remote fetch | Writeback commit wait | Trains? |
|---|---|---|---|---|
| loopback (unthrottled) | 1.1 s | 0.25 s | 0.44 s | yes |
| 1 Gbit/s | 6.0 s | 0.22 s | 5.1 s | yes |
| 500 Mbit/s | 10.8 s | 0.40 s | 9.7 s | yes |
| 200 Mbit/s | 27.3 s | 0.21 s | 26.4 s | yes |
| 100 Mbit/s | 51.5 s | 0.34 s | 50.7 s | yes |

The loss is identical at every bandwidth. Step time scales inversely with bandwidth (0.88 GB each way per
step). In this setting prefetch hides almost all fetch time, so the bottleneck is the writeback that
must commit before the next step uses the new parameter version. The real-link runs above, with a
smaller GPU budget and more remote layers, also expose fetch time.

## Interpretation

* **The research question is answered positively.** RAM on another machine moved the capacity frontier
  from 81.4M to 160.1M parameters on the same GPU under the same local budgets, with identical training
  mathematics.
* **On a commodity Wi-Fi link it is a capacity tool, not a throughput tool.** Steps take minutes. That
  could suit long, slow jobs where the alternative is not training the model at all. It is not
  competitive with a bigger GPU.
* The next limit is local RAM, not remote RAM. Gradients accumulate locally (4 B/parameter), so the
  local budget caps P_remote even with remote RAM to spare.
* The dominant cost is the optimizer round trip. Running AdamW where the state lives (on the RAM node)
  would remove most of it. That changes compute placement, so it is out of V2.5 scope.

## Not done / limitations

* Prefetch distances 1 and 2 at equal placement are not measured. fedora's free RAM fell below its
  reserve mid-run, and MeshTrain refused rather than paged.
* Budgets were scaled to the machines' free RAM (1/1.5/3.5 GiB instead of 2/4/8 GiB).
* One remote RAM worker. Multi-stage pipelines keep per-microbatch residency (layer-major reuse is
  single-stage only). MPS compute with remote RAM is untested.
* The planner's network cost estimates in these runs used half the probed bandwidth (fixed in
  `1aabb74`). That affects which layers it prefers to place remotely, not feasibility or correctness.
