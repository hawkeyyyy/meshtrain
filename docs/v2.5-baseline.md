## Capacity (2 GiB GPU budget, hard allocator cap)

From [v2-results.md](v2-results.md) (tiny_transformer hidden 1280, seq 64, batch 8 / 4 microbatches):

| Strategy | Largest trained | Step time there | Limited by |
|---|---|---|---|
| static (V1.5) | 81.4M | 108 ms | CUDA OOM at 160.1M |
| local-offload, AdamW on GPU | 160.1M | 1719 ms | CUDA OOM at 238.8M (AdamW state on the GPU) |
| auto local offload, CPU AdamW | **238.8M** | 1047 ms | **host RAM**: about 16 B/parameter (masters, gradients, AdamW state) |

Reproduced for this baseline (`runs/` trials on 2026-10-06, same settings):

| Strategy, size | Result | Loss after 3 steps |
|---|---|---|
| static 81.4M | trains, 88 ms/step | 7.024250268936157 (identical to v2-results) |
| static 160.1M | CUDA OOM | – |
| local-offload 160.1M | trains, 1332 ms/step, 1.68 GB peak | 7.07812237739563 (identical) |
| auto-offload 238.8M | **skipped by the host-RAM guard**: needs about 5.95 GB, 4.95 GB free | – |

The 238.8M point did not re-run. The machine had less free RAM than during the original run, and the
guard is now stricter (it includes measured process overhead). That is the same RAM ceiling the
remote tier is meant to lift.

## Known limitations going into V2.5

1. **Host RAM is the capacity ceiling** for local offload with the CPU optimizer (about 16 B/parameter).
2. **Redundant reloads**: with `after_use` eviction every offloaded layer is reloaded 2 × M times
   per step (M microbatches). That is 8–16 loads at the measured settings. Over a network this is
   prohibitive; V2.5 must reuse a loaded layer across microbatches.
3. Prefetch hides only up to the compute time. Steps are transfer-bound at these sizes.
4. Building a model allocates all its parameters on the CPU first, about 4 B/parameter transient.
5. MPS offload and multi-machine offload jobs are not measured.
