# MeshTrain V2.5: remote tensor memory

> MeshTrain exposes remote RAM as a managed backing tier for distributed tensor state.

This is **not** a shared physical memory space. GPU kernels only ever read the
local accelerator's memory. A tensor homed in remote RAM is explicitly fetched
over the network into local RAM, then copied onto the GPU, before any layer that
needs it computes. Updated values are written back and versioned before the
local copy may be dropped.

V2.5 answers one question: *can another computer's RAM let the same GPU train a
model that does not fit in its own VRAM plus a constrained local RAM budget?*
The measured answer is in [v2.5-results.md](v2.5-results.md).

```
   hawkey (compute)                                 fedora (RAM only)
   ┌─────────────────────────────┐   TCP (LAN/Wi-Fi) ┌──────────────────────┐
   │ RTX 4070  LOCAL_ACCELERATOR │                    │  TensorServer        │
   │   ▲ H2D / D2H (CUDA)        │  GET (fetch)  ◀────│  REMOTE_RAM          │
   │ local RAM LOCAL_RAM         │ ────▶ PUT (commit) │  per-job reservation │
   │   staging, grads, masters   │                    │  versions, crc32     │
   └─────────────────────────────┘                    └──────────────────────┘
```

Scope (unchanged rules): compute placement is static. Layer 17 computes on the
RTX 4070 for the whole job, and only its storage moves. There is no remote GPU
memory, no NVMe, no dynamic migration and no fault recovery.

## Memory tiers and homes

| Tier | Holds | Implemented |
|---|---|---|
| `LOCAL_ACCELERATOR` | weights in use, gradients of resident layers, activations | V2 |
| `LOCAL_RAM` | masters + AdamW state of locally homed layers, gradient accumulators, staging | V2 |
| `REMOTE_RAM` | masters + AdamW state of remotely homed layers | **V2.5** |
| `REMOTE_ACCELERATOR`, `LOCAL_NVME`, `REMOTE_NVME`, `RECOMPUTE` | – | raise `NotImplementedError` |

Each layer group has a *device residency* (HOT/COLD, from V2) and a *home*:

* **local home**: master weights + AdamW state in local RAM (V2 behaviour).
* **remote home**: master weights + AdamW state in REMOTE_RAM. Gradients still
  accumulate in local RAM: they are produced on this machine every microbatch,
  and sending them would double the traffic.

Remote homes require the CPU optimizer (`optimizer.execution: cpu_offload`, set
automatically by `memory.strategy: remote_offload`).

Priority (spec §12): accelerator, then local RAM, then remote RAM. Remote RAM is
used only for what does not fit locally.

## Authoritative-copy invariant

Every logical tensor has exactly one authoritative copy (`TensorMeta.tier`).
Cached copies are listed in `cached`. `dirty` means a faster copy is newer than a
slower backing copy. Remote example:

```
model.layers.7.qkv.weight   version 12
  between steps      tier REMOTE_RAM   cached {}                    p.data = empty placeholder
  staged for compute tier REMOTE_RAM   cached {LOCAL_RAM}           clean
  loaded on the GPU  tier REMOTE_RAM   cached {LOCAL_RAM, ACC}      clean
  after CPU AdamW    tier LOCAL_RAM    cached {}        dirty=True  (REMOTE copy stale)
  after commit v13   tier REMOTE_RAM   cached {LOCAL_RAM}           clean -> staging may be dropped
```

A dirty copy can never be dropped (`set_residency` raises). A layer is not
considered evicted until its new version is committed remotely.

## Host-side lifecycle (remote-homed layers)

```
REMOTE_ONLY ──fetch──▶ FETCHING_REMOTE ──▶ LOCAL_STAGED ──▶ (device lifecycle from V2:
     ▲                                        │   ▲          PREFETCHING → RESIDENT_ACCELERATOR → IN_USE …)
     │ drop staging (clean only)              │   │ commit (PUT accepted)
     └────────────────────────────────────────┘   │
                                    CPU AdamW ─▶ WRITEBACK_REMOTE
```

Transitions are explicit and validated (`ParameterGroup.host_transition`).
LOCAL_STAGED → FETCHING_REMOTE is allowed for fetching a staged layer's AdamW
state before the optimizer step.

## Tensor service protocol (`networking/tensor_server.py`)

Transport: the existing data-plane framing (magic + JSON header + raw payload,
`networking/protocol.py`) over TCP. The connection opens with a HELLO carrying
`command_kind: TENSOR_STORE` and the cluster token. A worker that lends RAM
serves it on its normal data-plane port. `meshtrain tensor-server` runs a
standalone RAM node.

| Op | Request meta | Reply |
|---|---|---|
| `RESERVE` | job, bytes | ok / `INSUFFICIENT_MEMORY` |
| `RELEASE` | job | bytes freed |
| `PUT` | job, tensor_id, old_version, new_version, crc32? + payload | committed version / `VERSION_CONFLICT`, `RESERVATION_EXCEEDED`, `CHECKSUM` |
| `GET` | job, tensor_id, version? | payload, version, crc32 / `VERSION_MISMATCH`, `NOT_FOUND` |
| `META`, `DELETE`, `HEARTBEAT`, `STATS`, `PING` | | |

* **Version protocol.** PUT is accepted only if `stored_version == old_version`
  (−1 means "must not exist"). It then advances the version atomically to
  `new_version`. A stale writer gets `VERSION_CONFLICT` and nothing changes.
* **Validation.** Dtype is checked against an allow-list. Shape × itemsize must
  equal the payload size. Ids are at most 200 characters. Messages have size
  limits. Optional crc32 is verified on PUT by the server and on GET by the
  client. Payloads are opaque bytes, and nothing is ever unpickled or executed.
* **Reservations.** A job reserves its remote bytes up front, before any model
  state is placed. The server refuses a reservation if it would exceed its
  lending budget or leave less free RAM than `reserve_system`. A job can never
  store more than it reserved. A job silent for `lease_s` (default 120 s) is
  released, so a crashed client cannot leak remote RAM.
* **Back-pressure.** The client has separate bounded connection pools for
  fetches (`max_inflight_fetches`) and writebacks (`max_inflight_writebacks`).
  Callers block instead of buffering. Fetched payloads land directly in pinned
  staging buffers.

Control plane vs data plane: a lending worker advertises total and available
RAM, its budget, reserved and used bytes, and the RAM kept for the OS in its
coordinator heartbeats. `meshtrain remote status --probe` shows these and
measures RTT and sustained bandwidth. Tensor bytes never travel through the
coordinator or JSON.

*Deviation from the spec:* the job's client sends the reservation straight to
the RAM worker's tensor service, which is the authoritative accountant. The
coordinator observes it through heartbeats rather than brokering it.

## Training step with remote layers

Every layer is placed one at a time while the stage is built. A layer homed
remotely is PUT as version 1 and leaves only an empty placeholder locally, so a
model larger than local RAM never exists in full on the compute machine. Then:

1. **Forward (layer-major, reuse on).** Layer L is fetched remote → local
   staging, copied to the GPU, and run for *all* microbatches. Then it is
   evicted from the GPU. Its staged copy stays while local RAM allows and is
   dropped (clean) under pressure.
2. **Backward.** Same order reversed. The layer is restaged if it was dropped.
   Gradients accumulate in local RAM, in the same microbatch order as the 1F1B
   single-stage schedule.
3. **Optimizer (CPU AdamW, one layer at a time).** Stage master + AdamW state,
   step, PUT params + state with `old → old+1`, and drop staging once committed.
   All writebacks are committed before the step returns. Every microbatch of
   the next step therefore sees the same, new parameter version.

Two-level prefetch: while layer L computes, layer L+1 is copied local → GPU
(`prefetch_distance`) and layers further ahead are fetched remote → local
(`remote_prefetch_distance`, default `prefetch_distance + 1`).

Reuse: without layer-major execution, `after_use` eviction fetches each remote
layer 2·M times per step (M microbatches). Layer-major execution needs about
2 per step, plus the optimizer fetch. `remote_reuse_ratio = 1 − remote fetches /
remote layer uses`.

## Planner (`planner/residency.py`)

1. Choose HOT layers within the GPU budget (V2 heuristic).
2. Start every layer locally homed. While the local RAM model does not fit,
   rehome the layer with the lowest *remote cost per local byte saved*:

       remote_cost = (fetches · P + 2·(1+k)·P) / network_Bps + requests · RTT

   HOT layers (fetched only for the optimizer step) move first. The network
   numbers come from a probe of the real link. Not optimal.
3. Check the remote bytes, `(1+k)·P` per remote layer, against the remote budget.

## Configuration

```yaml
memory:
  strategy: remote_offload
  accelerator_budget_mb: 2048
  local_ram_budget_mb: 4096
  remote_ram:
    enabled: true
    budget_mb: 8192
    workers: ["192.168.1.108:29500"]   # or preferred_workers: [fedora] via the coordinator
    max_inflight_fetches: 2
    max_inflight_writebacks: 2
    checksum: crc32
  reuse: {enabled: true}
  prefetch: {enabled: true, distance: 1}
```

On the RAM machine: `meshtrain join CODE --remote-ram-budget-mb 8192
[--remote-ram-reserve-system-gb 4]`, or `meshtrain tensor-server --budget-mb 8192`.

## Failure behaviour

* The RAM worker disappears or times out: the next remote operation raises
  `RemoteMemoryError`. The message names the worker, the error code, the
  affected remote layer groups, and a residency dump (step, fetches in flight,
  pending writebacks, per-layer states and versions). Training stops with that
  error. Remote RAM is released by the lease and local buffers are freed. No
  recovery is attempted (V2.5 scope).
* Every request has a timeout (`remote_ram.timeout_s`), so nothing waits forever.

## Security

**RemoteTensorStore is intended for trusted private-network peers in V2.5.** The
shared cluster token authenticates connections. Job and tensor ids, sizes and
dtypes are validated, and reservations bound memory use. There is no encryption
and no protection against a malicious peer that holds the token.

## Limitations

* Layer granularity. Each remote layer's whole parameter set moves as a unit.
* The optimizer step is the critical path: every remote layer's params and AdamW
  state go there and back (about 3·P each way) every step. On a commodity link
  this dominates step time ([v2.5-results.md](v2.5-results.md)).
* Layer-major reuse is used for single-stage jobs only. Multi-stage pipelines keep
  per-microbatch residency.
* Activations stay local and are not remote-offloaded. Recompute is not implemented.
* One remote RAM worker per stage. Spreading layers over several RAM workers is
  not implemented.
* MPS compute with remote RAM is untested (no Mac on the compute side).
